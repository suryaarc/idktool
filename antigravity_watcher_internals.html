Architecture notes

Watching a conversation while Antigravity writes it

Antigravity (Google's VS Code fork) keeps no public schema and exposes no event stream for its local chat history. antigravity_watch.py live-tails a conversation anyway, by asking SQLite one cheap question instead of hooking the process or polling a table on a timer.

~/.gemini/antigravity-ide/conversations/<uuid>.db table: steps column: step_payload (protobuf, no .proto)

01 · Mechanism

Ask PRAGMA data_version, not the filesystem

Every write Antigravity makes lands in a SQLite database running in WAL mode. Instead of statting the .db file or re-scanning the steps table on an interval, the watcher opens one read-only connection and repeats a single pragma:

SELECT data_version FROM pragma_data_version;
-- counter bumps only when ANOTHER connection commits to this file

That counter is exactly what Antigravity itself trips every time it writes a message, a tool call, or a status flip. It costs the same to check whether the database holds 41 rows or 1,276.

~6.7µsper data_version check, O(1) regardless of table size
0.25sdefault poll interval — 4×/sec, negligible at that cost
85 / 87-wal files newer than their .db on this machine — one by ~a month

Why not the .db file's mtime? In WAL mode, commits land in the -wal file and the base .db is only touched at checkpoint — it can lag real writes by hours or days. The -shm file looks tempting too, but it's touched merely by opening a connection: on this machine 19 idle sessions had -shm touched inside two minutes while only one had an actual -wal write, so ranking by it makes every idle session look live.

02 · Change detection

Rows don't just append — they also mutate in place

Antigravity writes conversations two different ways, and the watcher has to track both. A command-approval row is inserted once at status=9 and then flips to status=3 in the same row — no new row appears. A streaming assistant reply grows the same row's step_payload across dozens of commits as the answer streams in.

Why not fetch the payload every tick? Pulling step_payload on every commit measured ~296KB/tick on a large session — 8× slower than checking LENGTH() alone. The full blob is only fetched once, in flush_settled(), for rows that actually finished changing.

03 · Decode pipeline

Reading a protobuf with no .proto file

Antigravity's wire format is undocumented and private, so antigravity_chat_decoder.py walks it structurally: read the tag, recover the field number and wire type, and for length-delimited fields, guess what the bytes actually are by trying progressively less likely interpretations.

Step types, reverse-engineered empirically

No official schema exists for step_type or the field paths inside a decoded payload — these were confirmed by cross-checking two real conversations and 100+ steps. Unknown types fall through to a raw dump rather than being silently dropped.

04 · Session discovery

Picking the right .db out of dozens

Antigravity keeps one database per conversation, and can have many open. The watcher ranks candidates by real write activity, then re-checks periodically for a session that's decisively taken over — without flip-flopping when two sessions write in the same second.

05 · Output & safety

What comes out, and what never happens to the source

Console output is role-colored and capped — 20 lines per chat message, 6 per tool dump, since a single file read can run 700+ lines. Every event, untruncated, is also appended to a JSONL sink:

--json-out antigravity_watch.jsonl # append-safe, one record per line
--stats 30 # telemetry line every 30s
--raw # also dump step_types with no known shape

The quiet_ratio telemetry field is the whole design's report card: the fraction of polls where data_version hadn't moved and nothing was read. If that number isn't close to 1.0 on an idle session, the cheap-probe premise has failed.

  • Connection opened mode=ro — the watcher cannot write to Antigravity's database even by accident.
  • No transaction is ever held open across polls — a long-lived reader on a WAL database blocks checkpointing and lets -wal grow unbounded.
  • Antigravity's own process is never touched, hooked, or paused — purely a second reader on the same file.
